# ระบบน้ำใหม่ — greenfield

เริ่ม 2026-09-13 ตามคำขอให้เขียนระบบน้ำใหม่ ระบบเดิมเป็นหลักฐานย้อนหลัง
และใช้เทียบอาการได้ แต่ไม่เป็น implementation หรือคำตอบอ้างอิงของระบบใหม่
โค้ดใหม่อยู่ใน `water_v2/`; ไม่ import shaper, profile, bank repair หรือ ecology เดิม

## ข้อตกลงการออกแบบ

1. ใช้ DEM ในหน่วยบล็อกและ OSM เป็นข้อมูลตั้งต้น โครงข่ายเชื่อมด้วย source
   vertices ที่ใช้ร่วมกัน เส้นที่ตัดกันในภาพไม่ถูกเหมาว่าเป็นจุดบรรจบ
2. ทางน้ำขยับใน corridor จำกัดเพื่อเข้าแนวต่ำของ DEM ได้ จุดเชื่อมต้องคงที่
   ส่วนของเส้นนอกแผนที่ถูกตัดจริง ไม่บีบลงขอบ
3. แยกแอ่งน้ำนิ่งจากพื้นที่แบนกว้างและทางออก การเป็น polygon เดียวไม่แปลว่า
   เป็นทะเลสาบเดียว: source จริงมี component ที่สูงต่างกัน 80 บล็อก
4. แก้ระดับบนกราฟร่วมก่อนสร้าง geometry และส่งต่อคำตอบเดียวถึง writer
   เมื่อข้อจำกัดขัดกันให้รายงานพิกัด/สาเหตุ ไม่ก่อกำแพงหรือขุดหุบเพื่อปิด error
5. Product ระบุพื้น ก้นน้ำ ระดับน้ำ วัสดุ พืช และสถานะน้ำ source/flow/falling
   writer วางตามนั้นและ readback เทียบสถานะจริง ไม่บังคับว่าน้ำทั้งหมดต้องเป็น source
6. การคำนวณหนึ่ง scene มีขอบเขตบริบทชัดเจน การแบ่งเขียนเป็น tile ต้อง slice
   คำตอบ scene เดียวกัน ไม่แก้สมการใหม่ทุก tile และไม่อ้างว่า scene crop คือ global

## เกณฑ์ที่ใช้แทนการไล่ซ่อม metric

- topology คงเดิมเมื่อสลับลำดับหรือกลับทิศ source; ไม่มี junction ที่สร้างจากการเดา
- ระดับที่จุดบรรจบและแอ่งเป็นข้อมูลร่วม ไม่มีการ stamp เส้นทับกันแล้วเลือกระดับต่ำสุด
- ไม่มีการยกตลิ่งหลังแก้ระดับเพื่ออุดน้ำ; excavation มีขอบเขตและข้อขัดแย้งต้องเห็นได้
- น้ำไหลต้องมีแหล่งจ่ายตามระยะของบล็อกน้ำ แยกกรณีแอ่งนิ่งจากการเติม source ถี่ ๆ
- วัสดุ/พืชสร้างครั้งเดียวใน product; ไม่มี painter ตัดสินใหม่หรือวางหินทับความลึกภายหลัง
- test ของ solver, product และ block sink ใช้ตัวอย่างพฤติกรรมที่ต้องการ
  legacy tests ใช้กันผลกระทบระบบอื่น ไม่ใช้บังคับรูปแบบน้ำใหม่ให้เหมือนเก่า
- ก่อนใช้ในเซฟ: schema และ physical report ต้องผ่าน พร้อม backup และ readback
  หลังเขียน; visual และน้ำหลัง tick ต้องผ่านการตรวจในเกมแยกกัน

## โครงสร้างที่ใช้งานได้ — 2026-09-14

| โมดูล | หน้าที่ |
|---|---|
| `topology.py` | ตัด source ตามขอบ scene, คง node identity, หาเส้นใน corridor และหลบเส้นที่จัดไว้แล้ว |
| `levels.py` | ส่งข้อกำหนดระดับขั้นต่ำย้อนกราฟ แล้วแก้ระดับร่วมภายใต้เพดานตลิ่ง |
| `engine.py` | จำแนกแอ่ง, สร้างหน้าตัด/จุดบรรจบ, ระดับ/ความลึก, วัสดุ, พืช และแผน fluid |
| `model.py` | schema, ตรวจการเชื่อมต่อ/วงจร receiver, serialize และตรวจ hash |
| `blocks.py` | แปลง product เป็นบล็อกตามคำตอบที่ระบุ และเทียบ block states ที่อ่านกลับ |
| `scenarios.py` | รันพิกัดอ้างอิง 4 จุด สร้าง product, summary และแบบ comment JSON |

เส้นที่ตัดหรือแตะกันโดยไม่มีทางเชื่อมในแผนจะเป็น diagnostic แม้เป็นส่วนหนึ่ง
ของแม่น้ำเส้นเดียวกัน การจัดหน้าตัดเดินผ่านเฉพาะพื้นที่น้ำที่ต่อกัน และ receiver
ของทะเลสาบที่มีทางออกส่งต่อไปยังลำน้ำได้ ไม่บังคับให้ทะเลสาบทุกแห่งเป็น sink
ระดับที่ต้องการเป็น soft preference; solver ยกระดับได้ภายในเพดานที่ประกาศไว้
แต่ไม่แก้ DEM ฝั่งแห้งเพื่อทำให้ผ่าน

## วิธีรันซ้ำ

ใช้โฟลเดอร์ output ชื่อใหม่ทุกครั้ง ไฟล์ product เดิมเขียนทับไม่ได้:

```powershell
.\run.ps1 -m water_v2 scenarios --output-dir water_runs\my_water_candidate
.\run.ps1 -m water_v2 compile --bounds 5600 5984 5192 5576 --output water_runs\my_single_scene\steep_stream.npz
.\run.ps1 -m water_v2 inspect water_runs\my_water_candidate\steep_stream.npz --at 5792 5384
```

`scenarios` สร้าง `summary.json` และ `review.json` พร้อมพิกัด/ข้อขัดแย้ง
แต่ละจุด สถานะ comment เริ่มเป็น `not_tested`; ค่า Y รอจากฉากที่สร้างจริง
`compile` และ `scenarios` คืน exit code 2 เมื่อ physical gate ไม่ผ่าน
โดยเก็บ product ไว้ตรวจ ไม่ใช่รันสำเร็จแล้วข้ามจุดที่มีปัญหา

ข้อมูลตั้งต้นมีเพียง `terrain_y.npy` (หน่วยบล็อก) และ `water_sources.npz`
ไม่ใช้ระดับน้ำ/ความลึกจาก product เดิม ขนาด source แปลงที่ 4 เมตรต่อบล็อก
ไม่มีการลดความกว้างเพื่อบังคับให้ผ่าน gate บันทึก SHA-256 ของ input และโค้ด
ตรวจการเปลี่ยนระหว่างรัน และตรวจ product หลังเปิดอ่านกลับครบทุก scene
Product ปัจจุบันเป็น schema 2: metadata ของ report/settings/provenance ฝังใน NPZ
และต้องตรงกับ JSON ข้างไฟล์ การทดลอง schema 1 ต้อง compile ใหม่
สำหรับบันทึกความเห็นให้แก้ `review.json` ไม่แก้ manifest ของ product

## ขอบเขตการรับรอง

`ready_for_world_write` ในรายงานหมายถึงผ่านข้อจำกัดของ **scene compiler** เท่านั้น
ยังต้องมี world writer ใหม่และการตรวจ save ก่อนทดลองในเกม
ตัวแปลง `blocks.py` ยังไม่ได้จัดการ chunk, ล้างบล็อกเก่า, session lock, backup,
fluid ticks หรือ world reopen; จึงยังไม่ใช่คำสั่ง build/paint เซฟ

การคำนวณ supply ใช้แบบจำลองระดับผิวสองมิติ เป็น gate ขั้นต้น ไม่ใช่การจำลอง
vanilla fluid tick ครบทุกกฎ น้ำหลังเปิดเกมยังเป็น `pending` ทั้งหมด
ไม่เติม source ทุกช่องหรือเป็นช่วง ๆ เพื่อกลบ `unsupplied_water`
นอกจากนี้การตัด scene ยังไม่รักษา context ของทั้ง watershed; ไม่รับรอง global
หรือรอยต่อจากการ compile scene แยกกัน

ผลล่าสุดและข้อขัดแย้งจากข้อมูลจริงอยู่ใน [รายงานรอบใหม่](reviews/water_v2_20260914.md)
ลำดับต่อคือ W2: แก้การจำแนก basin, route ที่ยังชน และ supply บนช่วงราบให้มีเหตุผล
ทางกายภาพ ก่อน W3: writer แยกจาก legacy และการตรวจในเกม
เซฟทดลองวันที่ 13 กันยายนยังเป็นน้ำระบบเก่า ไม่มี water-v2 ถูกเขียนลงเซฟนั้น
