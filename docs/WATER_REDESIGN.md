# Water redesign — immersive-first

สถานะ: ระบบน้ำปัจจุบัน **ไม่ผ่าน visual acceptance** และห้ามถือว่าตัวเลข metric
ที่ดีขึ้นแปลว่าภาพในเกมดีขึ้น เอกสารนี้เก็บหลักฐานจาก patch `(6021, 6142)`
หลังรัน `build_terrain` และ `paint_surface` แบบเต็ม

## หลักฐานจากโลกจริง

### ลำธารและน้ำตก

- mask เป็นริบบิ้นทแยงกว้าง 3–4 บล็อกตาม buffer ของเส้น OSM
- ในกรอบเพียง 26×26 บล็อก ผิวน้ำไต่จาก Y=102 ถึง Y=142
- ที่ `(6021, 6142)` โลกจริงมี source-water ต่อเนื่อง Y=123..133 รวม 11 บล็อก
- ทั้งแผนที่มีกลุ่ม "น้ำตก" 3,346 กลุ่ม; 70.3% เป็นจุดเดี่ยว
- ม่านน้ำ 6,244 คอลัมน์ รวม 13,908 บล็อก สูงสุด 18 บล็อก

ข้อสรุป: นี่ไม่ใช่ระบบ waterfall แต่เป็นการเติมผนังน้ำเพื่อปิดขั้นของเส้นน้ำที่
ถูก drape บน DEM โดยไม่มี longitudinal river profile

### ทะเลสาบและตลิ่ง

- ทะเลสาบใหญ่สุดแบนที่ Y เดียวกันได้จริง
- แต่ 40.8% ของ dry bank ที่ติดทะเลสาบใหญ่อยู่ **ต่ำกว่าผิวน้ำ**
- dry bank ทั้งแผนที่ 16.9% อยู่ต่ำกว่าน้ำข้างเคียง
- painter เปลี่ยนวัสดุชายฝั่ง แต่ไม่เปลี่ยนรูปทรง terrain รอบฝั่ง
- ทะเลสาบใหญ่สุดมีพื้นที่ depth=31 (ชนเพดานสูตร) 26.3%

ข้อสรุป: ระดับน้ำ, bank terrain และ bathymetry ถูกคำนวณแยกกัน ภาพจึงเกิดผนัง
แนวตั้ง/ขอบน้ำลอย และก้นทะเลสาบมี plateau ที่ชน max-depth มากเกินไป

## Root causes

1. `fetch_landcover.py` รวม polygon ทะเลสาบและ directed waterway line เป็น
   landcover code `9` เดียวกัน ข้อมูลชนิดและทิศทางการไหลสูญหายถาวร
2. `make_water.py` ใช้ distance-to-shore สูตรเดียวกับน้ำทุกชนิด:
   wide river ถูกมองเป็น lake, shallow pond ถูกมองเป็น stream
3. `terrain_shape.py` เพียงกันน้ำจาก dither แต่ไม่ได้ carve channel หรือ reshape
   bank ดังนั้นน้ำถูกวางทับ DEM แทนที่จะเป็นส่วนหนึ่งของภูมิประเทศ
4. `make_water_levels.py` พยายามซ่อม graph หลัง rasterize แล้ว การ priority-flood
   แบบไร้ทิศทางจึงยกน้ำผิด branch และสร้าง outlet เชิงตัวเลข
5. `paint_surface.py` คำนวณ bed/bank/vegetation ตอนปลายเกินไป หลัง terrain ถูก
   build ไปแล้ว จึงแก้ geometry จริงไม่ได้
6. waterfall decoration ถูกสร้างจากทุก cardinal step ≥2 โดยไม่รู้ flow direction,
   rock lip, plunge pool หรือ channel width

## Pipeline ใหม่

```text
OSM water polygons ──> standing_water_mask ─┐
OSM directed ways ──> ordered centerlines ──┼─> hydrology_shape.py
base terrain_y + DEM valley context ─────────┘
                                      │
                                      ├─ final_terrain_y.npy
                                      ├─ water_mask.npy
                                      ├─ water_surface_y.npy
                                      ├─ water_depth.npy
                                      ├─ water_kind.npy
                                      ├─ flow_dir / velocity
                                      └─ waterfall_features.npz
```

`build_terrain.py` และ `paint_surface.py` ต้องเป็น consumer เท่านั้น ห้ามคำนวณ
ระดับน้ำหรือจำแนก lake/stream ซ้ำเอง

## ลำดับรื้อใหม่

1. แยก source data: waterbody polygon, river/stream/ditch และ ordered centerline
2. สร้าง river longitudinal profile ตามทิศ OSM + DEM โดย profile ต้องไหลลง
3. carve channel และ reshape bank ลง `final_terrain_y` ก่อน build
4. ทำ lake level + bank terrace พร้อมกัน แล้วค่อยสร้าง bathymetry
5. สร้าง waterfall เฉพาะ feature ที่ profile/terrain ยืนยัน พร้อม rock lip และ
   plunge pool; ห้ามเติมม่านจากทุก DEM step
6. ค่อยใส่วัสดุก้นน้ำ พืชน้ำ กก และ shoreline ecology จาก flow/velocity/exposure

## Acceptance gates

- ไม่มี dry bank ต่ำกว่าผิวน้ำข้างเคียง
- river profile ไม่มี local sink และไม่มีการยกผิวน้ำเหนือ bank
- step ≥2 เกิดได้เฉพาะ waterfall feature
- stream width ไม่เป็น buffer ribbon คงที่ตลอดสาย
- waterfall ต้องเป็น cluster ที่มี lip, curtain, plunge pool และ downstream reach
- lake max-depth cap ไม่กลายเป็น plateau กว้าง
- test patch ต้องผ่านทั้ง top-down, eye-level และการอ่านบล็อกจริงจาก world
- metric ทุกตัวต้องวัด artifact ที่เห็นจริง ไม่ใช่เพียง mask/probability

## Prototype acceptance — 2026-07-28

พื้นที่เดิม `(6021, 6142)` ใช้ output context 384 บล็อก แต่ build/paint เฉพาะ
256 บล็อก:

- source hydrology แยกเป็น waterbody 1,897,420 cells, waterway 918,867 cells
  และ ordered lines 4,882 เส้น; 98.75% ของเส้นไหลลงหรือราบตาม DEM ที่ปลายทาง
- footprint ลำธารใน patch ลดจาก buffer ribbon 867 cells เหลือ 480 cells ใน
  acceptance area และยังเป็น 4-connected
- dry bank ต่ำกว่าผิวน้ำ 0 จุด
- waterfall curtain มีเฉพาะ strong directed drop: 16 columns / 59 blocks ใน
  context; drop=2 ถือเป็น rapid และไม่สร้างม่าน
- actual world read-back ตรวจ 480 คอลัมน์น้ำ: missing 0, extra 0
- สุ่มตำแหน่ง footprint เก่าที่ถูกตัด 500 จุด: stale water 0
- vertical water run สูงสุด 7 บล็อกและตรงกับ declared waterfall; ของเก่าที่
  `(6021, 6142)` เป็น source-water pillar 11 บล็อก
- ลำธารและม่านน้ำยังเขียนเป็น source water `level=0` ทั้งหมด แต่ฝัง scheduled
  `fluid_ticks` ลง chunk ให้ Minecraft update เองตอนโหลด; acceptance patch มี

## Feedback จากโลกจริง — 2026-07-29

ผู้ใช้ตรวจพื้นที่ที่ paint ด้วย `hydrology_global/` แล้วรายงานสองอาการ:

1. บล็อกรอบสายน้ำและแอ่งน้ำ **ถูกยกสูงขึ้น** ไม่ blend กับ terrain รอบข้าง
2. น้ำที่ไหลลงทะเลสาบ **บางจุดลดลง 1 บล็อกทันที** ทำให้ไม่ smooth

### สาเหตุที่ยืนยันแล้ว และแก้ไปแล้ว

`shape_hydrology_global` ส่ง `max_drop_per_sample=6.0` และ
`max_surface_step=12` ทับ default ของ patch (2.0 / 4) — acceptance ข้างบนจึง
ผ่านทั้งที่ของจริงหยาบกว่าสามเท่า ดู DECISIONS.md หัวข้อ "global ต้องใช้
พารามิเตอร์ชุดเดียวกับ patch" ตอนนี้มี parity test บังคับไว้แล้ว

### อาการ 1 — แก้แล้ว: ตลิ่งต้องเฟดกลับ ไม่ใช่ตัดจบ

เดิมมีสามชั้นยกพื้นรอบน้ำทับกัน และไม่มีชั้นไหน taper ออก

| จุด | ทำอะไร (เดิม) |
|---|---|
| `shape_hydrology_patch` (dry edge lift) | ยกทุกบล็อกแห้งที่ติดน้ำให้ถึงระดับผิวน้ำ ไม่มีเพดาน |
| `shape_standing_water_patch` (lake bank) | ยกเป็นขั้นถึง `near_stage+3` ในระยะ `bank_width` แล้ว**ตัดจบทันที** |
| `shape_waterway_patch` (stream bank) | clip terrain ทั้งบนและล่างเข้าช่วงแคบรอบระดับน้ำ |

ตัวการคือ `minimum = near_stage + (d - 1)` ซึ่ง **สูงขึ้นตามระยะ** แล้วตัดจบที่
`bank_width` บนทะเลสาบไหล่เขาที่พื้นข้างลาดลง ทั้งแถบจึงถูกยกเป็นสันเหนือผิวน้ำ
แล้วเกิดหน้าผาที่ขอบแถบ

ทั้งหมดเกิดจากการไล่แก้ metric "dry bank ต่ำกว่าผิวน้ำ 40.8%" ซึ่งแก้ตัวเลขได้
(patch วัดได้ 0 จุด) แต่วิธีแก้คือยกพื้นเป็นสัน จึงย้ายปัญหาไปเป็น artifact ที่
ตาเห็นแทน — ตรงกับที่เอกสารนี้เตือนไว้เองว่าห้ามเชื่อ metric แทนภาพ

ตอนนี้ใช้ `bank_taper_weight` ตัวเดียวคุมทั้งการยก (`taper_bank_lift`) และการกด
(`taper_bank_cut`): ยกเต็มที่ระยะ `BANK_SEAL_BLOCKS` เท่าที่กันน้ำรั่ว แล้วลด
น้ำหนักเชิงเส้นจนเป็นศูนย์พอดีที่ `BANK_BLEND_BLOCKS` พื้นที่สูงกว่าผิวน้ำอยู่แล้ว
ไม่ถูกแตะเลย หน้าผาธรรมชาติจึงยังอยู่ครบ

วัดบนทะเลสาบไหล่เขาผังเดียวกัน:

| | ยกสูงสุด | ขั้นบนพื้นแห้งสูงสุด | รูรั่ว |
|---|---|---|---|
| เดิม | 7 | **9** | 0 |
| ใหม่ | 2 | **3** | 0 |

`tests/test_hydrology_shape.test_bank_lift_seals_edge_without_building_a_ridge`
คุมทั้งสามเงื่อนไข (กันรั่ว / ห้ามยกเหนือผิวน้ำ / ห้ามมีขอบคม) และผ่าน mutation
test แล้ว

### อาการ 2 — แก้แล้วในโค้ด รอวัดบน global: pool quantization

`regularize_stage` บังคับแค่ว่าห้ามไหลขึ้น แล้วปล่อยให้ stage ไต่ตาม DEM ทีละ
บล็อก ลำธารจริงเป็นขั้นบันได: ช่วงราบยาว (pool) สลับกับจุดตก ไม่ใช่ลาดทีละ 1
ต่อเนื่อง — baseline เดิมก็วัดได้ว่า "ขั้น 1 บล็อก 12.4%" ซึ่งมากพอจะสะดุดตา
ตลอดสาย

**ยังไม่ลงมือแก้เพราะยังไม่มีตัวเลขว่าขั้นกระจายอย่างไรจริง** การออกแบบ
quantisation โดยเดาเสี่ยงซ้ำรอยเรื่อง halo (เดาว่าเป็นสาเหตุ วัดแล้วไม่ใช่)
ทางที่แย่ที่สุดคือรวมขั้นถี่ ๆ ให้เป็นขั้นใหญ่ขึ้น เพราะจะกลายเป็นน้ำตกเทียม
แทนที่จะเป็นแอ่ง

`report_metrics.stream_metrics` จึงเพิ่มตัววัดตรงอาการก่อน:

| ตัวเลข | ความหมาย |
|---|---|
| `pool_size_median` | ความยาวแอ่ง (ช่วงที่ผิวน้ำระดับเดียวกัน) ตรงกลาง |
| `pool_size_p90` | แอ่งยาวสุดในกลุ่มบน |
| `tiny_pool_share` | สัดส่วนแอ่งที่มี <=2 cells — **สูง = น้ำลดทีละบล็อกแทบทุกก้าว** |

แยกสองกรณีได้ชัด (ยืนยันด้วยเทสต์): ลำธารที่ลดทีละบล็อกได้ median 1 /
tiny 100% ส่วนลำธารที่มีแอ่งยาว 8 บล็อกได้ median 8 / tiny 0%

ต้องรัน `hydrology_shape.py --global` ใหม่แล้ววัดด้วยตัวเลขชุดนี้ก่อน จึงจะรู้ว่า
ควร quantise แรงแค่ไหนและตรงไหน

**อัปเดต:** การ quantise ลงมือทำไปแล้วและอยู่ในโค้ด — `quantize_stage_pools`
รวบขั้นเป็นแอ่งยาวอย่างน้อย `MIN_POOL_BLOCKS` (8) โดยมีเพดานสองชั้นกันการ
"ก่อเขื่อน": `bank_confinement` จำกัดให้ขังน้ำเหนือพื้นได้เท่าที่ตลิ่งจริงขังไหว
และ `local_narrow_points` ผลักจุดตกไปอยู่ช่วงที่ลำน้ำแคบ ไม่ใช่กลางผืนกว้าง
ทั้งสามมีเทสต์คุมแล้ว  **ที่ยังค้างคือการวัดบน global** ตัวเลข
`pool_size_median` / `tiny_pool_share` ของผังเต็มยังไม่ถูกบันทึกที่ไหน

## รอบตรวจ logic — 2026-08-12

ตรวจโค้ดเทียบเอกสารแล้วแก้สองข้อที่เป็นเหตุผลเชิงตรรกะล้วน (มีเทสต์คุมทั้งคู่):

- **envelope กับการยุบหน้าตัดต้องวนจนลู่เข้า** ไม่ใช่ทำอย่างละครั้ง — การยุบ
  เปิดช่องว่างที่ envelope ปิดไปแล้ว วัดได้ 1 จุดบนผังทดสอบ ดู DECISIONS.md
- **pin ของปากทะเลสาบต้องแผ่ไปทั้ง run** ไม่งั้นสองแกนยกและกดสลับกันจนหมด
  จำนวนรอบ แล้วคืนหน้าตัดที่ยังไม่ราบ

และเพิ่มเทสต์คุมสองการแก้ที่ทำไว้ก่อนหน้าแต่ยังไม่มีอะไรตรึง: การจัดกลุ่มน้ำนิ่ง
บนผืนเต็มก่อนตัดร่องลำน้ำ (สองฝั่งเคยได้ระดับ 39/40 คนละค่า — ยืนยันว่าเทสต์จับ
ของเดิมได้) และเกณฑ์หน้าผาที่สูงขึ้นเฉพาะริมลำน้ำใน `paint_surface`

   แต่ละเส้นอิสระจากกัน แต่ละเส้น monotone ในตัวเอง แต่ไม่มีอะไรบังคับว่าสาขา
   ต้องจบที่ระดับของสายหลักตรงจุดบรรจบ ต้องไล่ topological order บนกราฟที่
   `accumulate_upstream_length` มีอยู่แล้ว แล้วส่งระดับปลายน้ำเป็น boundary

3. **`STREAM_CLIFF_MIN_DROP` เป็น stopgap** — มันซ่อนตลิ่งลายชั้นหินได้ แต่หน้าตั้ง

### ตลิ่ง — แก้ต่อในรอบเดียวกัน

วัดทีละขั้นแบบเดียวกัน (ห่อ `taper_bank_lift` / `taper_bank_cut` แล้ววัดตลิ่ง):

| ขั้นตอน | ตลิ่งที่ปีนเกิน 1 บล็อก | ขั้นสูงสุด |
|---|---|---|
| DEM ดิบ | 5% | 4 |
| หลัง `taper_bank_lift` | 7% | 4 |
| **หลัง `taper_bank_cut`** | **31%** | **24** |

สองสาเหตุคนละชั้น แก้ทั้งคู่:

1. **เพดานการกดเป็นการ *คูณ*** — `cut = excess * weight` โดย weight ไล่ 1->0
   ตามระยะ ขนาดการกดจึงแปรตาม `excess` ซึ่งบนไหล่เขาสูงถึง 40 บล็อก วงที่ห่างกัน
   1 บล็อกจึงถูกกดต่างกัน ~5 บล็อก = บันไดหิน  เปลี่ยนเป็นเพดาน **บวก**
   (`min(excess, (blend - distance) * rise)`) ขั้นระหว่างวงจึงไม่เกิน `rise`
   ต่อบล็อกเสมอ ไม่ว่า excess จะใหญ่แค่ไหน — ขั้นสูงสุด 24 -> 4
2. **ตลิ่งลอกขั้นของน้ำมาทั้งดุ้น** — เพดานอิงระดับน้ำของ cell นั้นตรง ๆ ตลิ่ง
   วงแรกจึงเสมอผิวน้ำพอดี  วัดได้ว่าขั้นตลิ่งที่ปีนไม่ได้ **ทุกจุด** อยู่ห่างน้ำ
   1 บล็อก และขั้นขนาด 2 บล็อก 802 จุด ตรงกับขอบผิวน้ำที่ตก 2 บล็อก 1,410 จุด
   ใช้ระดับน้ำสูงสุดในละแวก `BANK_TERRACE_BLOCKS` (5) แทน ตลิ่งจึงเป็นขั้นบันได
   ยาว ๆ และยังไม่มีทางต่ำกว่าผิวน้ำของ cell ตัวเอง (ไม่รั่ว) — 27% -> 13%

**ทางที่ลองแล้วไม่เอา**: ลด `UNSUPPORTED_MAX_STEP` 2 -> 1 ให้ผิวน้ำเรียบขึ้น
ตลิ่งดีขึ้นมาก (27% -> 9%) แต่ envelope ไม่สามารถกดขั้นให้ต่ำกว่าเกณฑ์ม่านน้ำได้
ภายใน `MAX_ENVELOPE_INCISION` จึงเกิดขั้น >4 ที่ไม่มีม่านปิดจริง ๆ (parity test
จับได้) — ค่าคงที่สองตัวนี้ผูกกัน: ต้องมี `UNSUPPORTED_MAX_STEP + 1 >=` เกณฑ์
สร้างม่าน มิฉะนั้นจะมีช่วงที่ตกแรงได้แต่ไม่มีอะไรปิด

### `unflat_cross_runs` — metric ผิดเอง แล้วเจอของจริงข้างใต้

ตัวเลขนี้ค้างที่ 134-250 ต่อ patch มาตลอด แยกดูแล้วพบว่า **98% เป็นการออกแบบ
ไม่ใช่การละเมิด**: run ที่ระดับต่างกันเกิน 2 บล็อกคือลำน้ำที่วิ่งเกือบขนานแกน
ซึ่ง `MAX_SECTION_SPREAD` สั่งห้ามยุบตั้งแต่รอบที่แล้ว (ยุบแล้วได้ปล่องหิน)
metric ยังใช้นิยามเก่าที่นับทุก run ที่ไม่ราบ

| จุด | run ที่ไม่ราบ | spread<=2 (ของจริง) | spread>2 (ตามการออกแบบ) |
|---|---|---|---|
| hill_junction | 213 | 3 | 210 |
| steep_stream | 250 | 2 | 248 |
| prototype_stream | 134 | 0 | 134 |

แก้ metric ให้ใช้เกณฑ์เดียวกับอัลกอริทึม (อ่านค่าคงที่จาก `hydrology_shape`
ที่เดียว) และหา run บน `way` เต็มก่อนค่อยกรองด้วย core — ไม่งั้นขอบ core จะตัด
run ที่ยาวเกิน 16 ให้สั้นลงจนเข้าเกณฑ์แล้วถูกนับผิด

เหลือของจริง 0-8 run ต่อ patch แล้วขุดต่อพบสองอย่าง:

1. **ลูปจบก่อนลู่เข้า** — รันการยุบหน้าตัดซ้ำบน *ผลสุดท้าย* ของ flat_river ยัง
   เปลี่ยนอีก 237 cell  `SURFACE_FIXPOINT_PASSES` 4 -> 16
2. **ปากน้ำถูกดึงกันไปมา** — การยุบยก cell ปากน้ำขึ้นหาระดับทะเลสาบทุกรอบ
   (pin) ส่วน envelope กดลงทุกรอบ จึงไม่มีวันนิ่ง  ต้องยกเว้นปากน้ำจาก envelope
   ด้วย (`unlimited = supported | has_mouth`) ไม่ใช่ยกเว้นแค่ในการยุบ

ผล: `unflat_cross_runs` เหลือ 0 ใน 7 จาก 9 จุด (flat_river 5, lake_corridor 1)
และ `uncovered_drop` ลดอีก (steep_stream 8 -> 1, cliff_bedding 2 -> 0)

**ยังเหลือ 6 run ทั้งชุดที่อธิบายไม่ได้** — ~0.1% ของ cell น้ำ บันทึกไว้ว่ายัง
ไม่ได้ไล่ต่อ ไม่ใช่ว่าแก้หมดแล้ว

### ไล่ 6 run ที่เหลือจนจบ

`unflat_cross_runs` เหลือ 6 run ทั้งชุด (flat_river 5, lake_corridor 1) ไล่ต่อแล้ว
พบว่าเป็นการวนไม่ลู่เข้าที่ยังไม่หาย: รันการยุบหน้าตัดซ้ำบนผลสุดท้ายของ
flat_river ยังเปลี่ยนอีก **141 cell** แม้วนไปแล้ว 16 รอบ

ต้นเหตุ: **การแผ่ pin มีอายุแค่ในการเรียกครั้งเดียว** `flatten_cross_sections`
copy อาร์เรย์ `locked` ทุกครั้ง (ตั้งใจ ไม่ให้ไปแก้ของผู้เรียก) cell ที่ถูกยกขึ้น
หาระดับทะเลสาบในรอบนี้จึงกลายเป็น cell ธรรมดาในสายตาของ envelope รอบถัดไป
มันกดกลับลงมา แล้วการยุบก็ยกขึ้นใหม่ — วนแบบนี้ไปจนหมดจำนวนรอบ

การยกเว้น `has_mouth` จาก envelope (แก้ไปแล้วรอบก่อน) ไม่พอ เพราะครอบเฉพาะ
cell ปากน้ำต้นฉบับ ไม่ครอบ cell ที่รับระดับทะเลสาบต่อมา

แก้ด้วย `propagate_locked=True`: การวนคู่กันเก็บ pin ที่แผ่แล้วไว้ใช้รอบถัดไป
และ envelope ยกเว้น `locked != UNRESOLVED` ทั้งหมด ไม่ใช่แค่ `has_mouth`

ผล: `unflat_cross_runs` = **0 ทั้ง 9 จุด** และผลลัพธ์นิ่งจริง (ยุบซ้ำเปลี่ยน 0 cell
ทุกจุดที่ตรวจ) ส่วน `uncovered_drop` เหลือ 4/4/1 ที่สามจุด

pin แผ่กว้างแค่ไหน: ที่ flat_river จาก 131 -> 1,961 cell (53% ของลำน้ำ) ซึ่ง
**ยอมรับได้เพราะการแผ่ผ่านได้เฉพาะ run ที่ระดับต่างกันไม่เกิน 2** มันจึงคือผิว
ทะเลสาบที่ต่อเนื่องกันจริง ไม่ใช่การลากระดับทะเลสาบขึ้นไปทั้งลำน้ำ

**การแก้นี้ไม่มี unit test คุม** — ลองสร้างผังสังเคราะห์สองแบบแล้วทั้งคู่ลู่เข้า
ได้เองโดยไม่ต้องใช้ flag  ตัวที่คุมคือ golden metric: ปิด flag แล้ววัดใหม่ได้
flat_river 5 / lake_corridor 1 กลับมาทันที เปิดแล้วเป็น 0 ทั้งคู่ — `compare`
จะจับได้เพราะ `unflat_cross_runs` เป็นตัวที่ต้องเป็นศูนย์ (ไม่มีธรณีประตู)

เปลี่ยนเป็น "ต้องเดินไกลแค่ไหนน้ำถึงลง 2 บล็อก" แล้วช่วงกลางก็โผล่มา

## ที่ลองแล้วไม่ได้ผล: ย้ายร่องลึกออกจากกึ่งกลางหน้าตัด — 2026-08-18

สมมติฐาน: `bed_flat_share` (cell ที่ลึกเท่าเพื่อนบ้านทุกทิศ) ลดไม่ได้เพราะหน้าตัด

| จุด | ก่อน | หลัง |

## `bed_flat_share` — ไล่จนจบแล้ว: เป็นเมตริกที่ใช้เป็นด่านไม่ได้ — 2026-08-18

ไล่สามรอบ ทุกรอบวัดผล:

| ที่ลอง | ผล |
|---|---|
| ย้ายร่องลึกออกจากกึ่งกลาง (ทุกความกว้าง) | **แย่ลง** 0.57 -> 0.63 — ลำน้ำ 2-3 cell ถูกดันจนจุดลึกสุดหลุดออกนอกน้ำ |
| ย้ายร่องลึกเฉพาะหน้าตัดกว้าง (half >= 1.5) | **ไม่เปลี่ยนเลย** — ไม่มีหน้าตัดไหนในแผนที่กว้างถึงเกณฑ์ กลายเป็นโค้ดตาย |
| บังคับให้ขอบตื้นกว่ากลาง 1 บล็อก | **แทบไม่ขยับ** 0.43 -> 0.42 |

เปิดข้อมูลจริงดูแล้วพบว่าหน้าตัด **มีรูปทรงอยู่แล้ว**: ที่ flat_river หน้าตัดกว้าง
3 cell เป็น `[2, 3, 2]` แทบทุกอัน  ความ "แบน" ที่เหลือมาจากเรขาคณิตของกริด —
ลำน้ำที่วิ่งทแยง เพื่อนบ้านสี่ทิศของ cell กลางกลายเป็น cell กลางของหน้าตัดถัดไป
(ลึกเท่ากัน) ส่วนขอบอยู่ในแนวทแยงซึ่งไม่ถูกนับ  เมตริกจึงวัด "ช่วงลำน้ำที่รูปทรง
ซ้ำกันตามแนวไหล" ซึ่งเป็นสิ่งที่แม่น้ำจริงเป็น ไม่ใช่ข้อบกพร่อง

ตัวควบคุมยืนยันอีกทาง: ก้นน้ำที่สร้างตามลำดับแอ่ง-แก่งตามตำรา (5-7 เท่าของความ
กว้าง) ได้ 0.34 ที่กว้าง 1 cell และ 0.00 ที่กว้าง 3 cell

**ข้อสรุป**: `bed_flat_share` ใช้เป็น *บริบท* ได้ (ค่าที่พุ่งขึ้นแปลว่ามีอะไร
เปลี่ยน) แต่ **ใช้เป็นด่านผ่าน/ไม่ผ่านไม่ได้** และเป้า <=0.25 ไม่มีความหมาย

จริงคือ `bed_flat_lake` (ก้นทะเลสาบแบน ซึ่งกริดไม่ได้บิดเบือน)
